# Problems Workflow

This document describes the problems/testcases pipeline: discovery → generate → validate → export → seed. It explains file layout, responsibilities, and commands for adding new problems (up to 100) and seeding into Supabase.

## Key scripts
- `scripts/discoverPatterns.ts` — scans the dataset (`datasets/LeetCodeDataset-v0.3.1-train.jsonl`) and writes `data/pattern-discovery-report.json` with supported problem slugs and inferred patterns.
- `scripts/generateTopSupportedProblems.ts` — uses the discovery report and the dataset to write problem folders under `data/problems/<slug>/` containing `problem.json` and `testcases.json`. It filters out slugs already present in `data/existing-problems.json` before applying `START` and `LIMIT`.
- `scripts/generateProblems.ts` — lower-level generator for custom runs (see inline help in file).
- `scripts/validateProblems.ts` — runs all validators (schema, testcases ordering/visibility, reference-solver checks) and exits non-zero on failure.
- `scripts/validateTestcases.ts` — testcases-specific checks (contiguity, visibility, ordering).
- `scripts/validateReferenceSolutions.ts` — runs built-in reference solvers against public testcases to ensure consistency.
- `scripts/exportExistingProblems.ts` — collates all problems under `data/problems` into `data/existing-problems.json`.
- `scripts/seedProblems.ts` — upserts problems into Supabase and (re)writes problem_test_cases; reads `PROBLEMS_ROOT` env or defaults to `data/problems`.

## Files layout
- `data/problems/<slug>/problem.json` — problem metadata and examples.
- `data/problems/<slug>/testcases.json` — `{"test_cases": [...]}` with `order`, `visibility`, `display_input`, `display_output`, `input`, `expected_output`.
- `data/pattern-discovery-report.json` — generated by discovery stage.
- `data/existing-problems.json` — aggregated export used for tracking.

## Testcases architecture
See `docs/TESTCASES_ARCHITECTURE.md` (detailed). Briefly:
- `input` and `expected_output` are normalized strings matching the `input_format` and `output_format` declared in `problem.json`.
- `display_input` / `display_output` keep original raw dataset strings for traceability.
- `visibility` is `PUBLIC` for the first three cases, `PRIVATE` afterward.
- `order` must be contiguous starting from 1; validators enforce this.

## Typical workflow (add up to 100 problems)
1. Run discovery (once):
   ```powershell
   npx tsx scripts/discoverPatterns.ts
   ```
2. Generate a slice (use `START` and `LIMIT`, e.g., first 100):
   ```powershell
   $env:START='0'; $env:LIMIT='100'; npx tsx scripts/generateTopSupportedProblems.ts
   ```
3. Run validation:
   ```powershell
   npm run validate
   ```
   - Fix any reported issues. Validators check schema, contiguity, and reference-solver outputs.
4. Refresh the live-set export so the next generation pass can exclude already-seeded problems:
   ```powershell
   npx tsx scripts/exportExistingProblems.ts
   ```
5. Generate the next 10 new problems into a staging folder, excluding the live set:
   ```powershell
   $env:PROBLEMS_ROOT='data/staging-new'; $env:EXISTING_PROBLEMS_PATH='data/existing-problems.json'; $env:START='0'; $env:LIMIT='10'; npx tsx scripts/generateTopSupportedProblems.ts
   ```
   - Start from an empty staging folder if you want only the new batch. The generator will skip any slug already present in `existing-problems.json`.
6. Validate the staging batch:
   ```powershell
   $env:PROBLEMS_ROOT='data/staging-new'; npm run validate
   ```
7. Seed to Supabase from the staging folder only, after review and backup if needed:
   ```powershell
   $env:PROBLEMS_ROOT='data/staging-new'; npx tsx scripts/seedProblems.ts
   ```

## Notes & Best Practices
- All JSON reads strip Windows BOMs to avoid `JSON.parse` errors.
- Prefer small staged batches (10–100) and only seed after full validation.
- If you need to re-seed the same set, `seedProblems.ts` upserts by `slug` and deletes/rewrites `problem_test_cases` for the problem.
- To revert an accidental seed, you must use Supabase console or write a reverse script; seeding does not currently record audit logs in the DB.
